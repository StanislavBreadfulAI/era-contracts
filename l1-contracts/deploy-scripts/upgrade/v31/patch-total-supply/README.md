# v31 `totalSupply` fix — upgrade-data patch

This directory holds the tooling that patches the **already-prepared v31 upgrade data** after
the base-token `totalSupply` fix in `L2AssetTracker`
(`_needToForceSetAssetMigrationOnL2` no longer reads the base token `totalSupply()` before it
is backfilled).

## Why the upgrade data has to be patched

The fix changes the compiled **L2AssetTracker** bytecode. Several L2 genesis/upgrade contracts
embed the L2AssetTracker bytecode hash in their own bytecode, so re-running the hash tooling
(`yarn calculate-hashes:fix`) shows that **more than one** deployed-bytecode (zk) hash changes:

| Contract | role |
| --- | --- |
| `L2AssetTracker` | the fixed contract; its hash is in `FixedForceDeploymentsData.assetTrackerBytecodeInfo` |
| `L2GenesisUpgrade` | genesis/upgrade entry point that pulls in the asset tracker |
| `L2GenesisForceDeploymentsHelper` | force-deploys the L2 system contracts |
| `L2ComplexUpgrader` | runs the force-deploy-and-upgrade |
| `L2V30TestnetSystemProxiesUpgrade` | testnet upgrade contract that references the asset tracker |

(Only these five `zkBytecodeHash` values change — every other entry in `AllContractsHashes.json`
is byte-identical. This is exactly the "not only the L2 asset-tracker code hash could be
affected" case.)

Those hashes are baked into the v31 upgrade data the Era `ChainTypeManager` stores:

- the v31 upgrade `DiamondCutData` registered with `setNewVersionUpgrade` (its post-upgrade
  calldata embeds the L2 `FixedForceDeploymentsData`), and
- the `ChainCreationParams` set with `setChainCreationParams` (its `forceDeploymentsData`
  embeds the same `FixedForceDeploymentsData`).

So after the fix we must (a) re-register the corrected upgrade cut, (b) update the chain
creation params used for newly-created chains, and (c) re-run the upgrade on chains that
already executed the buggy v31 upgrade so they force-deploy the corrected bytecode.

## What the scripts do

A zk bytecode hash is a unique 32-byte value, so the patch is a **find-and-replace of the old
hash with the new hash** inside the previous proposal's calldata — no fragile deep re-encoding
of the nested structs, and trivial to reproduce in two independent implementations.

- **`PatchTotalSupplyV31UpgradeData.s.sol`** (Solidity / forge) — the authoritative script.
  Reads the previous proposal, computes the new hashes **from the build artifacts**
  (`zkout/*`), replaces every stale hash, and emits the patch `Call[]`:
  1. `setUpgradeDiamondCut(patchedCut, oldProtocolVersion)`
  2. `setChainCreationParams(patchedParams)`
  3. `executeUpgrade(chainId, patchedCut)` for every already-upgraded chain.
- **`../../../../scripts/patch-total-supply-crosscheck.ts`** (TypeScript) — re-derives exactly
  the same `Call[]`, but reads the new hashes **from `AllContractsHashes.json`**. It then
  asserts `keccak256(abi.encode(Call[]))` equals the Solidity output. Because the two
  implementations take the new hashes from *different* sources (artifacts vs. the hashes JSON),
  an identical result also proves `AllContractsHashes.json` is consistent with the artifacts.

## Inputs

| file | meaning |
| --- | --- |
| `config.json` | Era CTM address, old/new protocol versions, verifier, genesis upgrade, chain ids, and the list of already-upgraded chains to patch |
| `previous-bytecode-hashes.json` | the L2 contract zk hashes that the **previous** v31 release deployed (pre-fix) |
| `previous-upgrade-data.json` | the previous proposal as `{ "calls": abi.encode(IProtocolUpgradeHandler.Call[]) }` |

`previous-upgrade-data.json` here is a **representative fixture** generated by
`forge script … --sig generateExampleProposal()` from `previous-bytecode-hashes.json` +
`config.json`, so the whole flow is reproducible in CI without access to a live environment.
To patch a real proposal, replace `previous-upgrade-data.json` with the actual stored proposal
calls and set `config.json` to the real environment values; the patch logic is unchanged.

## Outputs (git-ignored, regenerated on each run)

- `patched-calls.sol.json` — `{ encodedCalls, callsKeccak }` from the Solidity script.
- `patched-calls.ts.json` — the same from the TypeScript script.

## Reproduce

From `l1-contracts/` (with the pinned foundry-zksync on `PATH`, the `zkout` artifacts rebuilt
with the fix, and `AllContractsHashes.json` regenerated):

```bash
./deploy-scripts/upgrade/v31/patch-total-supply/run-and-crosscheck.sh
# or:
yarn patch-total-supply:crosscheck
```

The run ends with `CROSS-CHECK OK` when the Solidity and TypeScript outputs match.
